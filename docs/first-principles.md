# 第一性原理解析：dsh-codex-approval

> 目的：不从功能清单出发，而从**接缝契约给出的硬约束**出发，推导这个插件的每个组成部分为什么"必然长成这样"，并标出哪些是真正的设计选择。
>
> 验证快照：插件 `v0.4.4`（提交 `1a4b99a`）；宿主 DSH `0.2.0-rc.2`；本机审计日志 `~/.dsh/logs/approval.jsonl`（684 行 / 196 次决策）。
>
> 标注约定：**（契约）**= 宿主源码可查的事实；**（源码）**= 本插件源码可查的事实；**（实测）**= 本机日志的统计；**（推断）**= 我的推理，未经受控实验。

---

## 1. 起点：接缝交付了什么

插件的形状由接缝决定，不由作者口味决定。先把接缝的四条硬约束摆出来。

### 1.1 请求载体是贫瘠的（契约）

`ApprovalService.request(req)` 收到的 `req` 只有：
`{ agent, toolName, callId?, reason?, signal }`
——`dsh-user-approval/lib/index.js:130-145`

**没有**工具参数、没有 cwd、没有目标路径、没有"副作用描述"。原因也清楚：宿主不知道也不该假装知道一个工具调用会做什么；它只知道"有个操作被沙箱拦下来了"。

→ **推论 A**：任何基于"操作内容"的判定，都必须先自己重建证据。这就是 `enrich.js` 存在的**唯一**理由：按 `callId` 回查会话日志里最新 `assistant/message` 的 `tool-call` 分片，把 `arguments` JSON 反序列化回来（`enrich.js:40-61`）。

### 1.2 返回语义是封闭且 fail-closed 的（契约）

```
OUTCOMES = ["allowed-once", "rejected", "cancelled", "unavailable"]
```
- waterfall 的末位默认值是 `"unavailable"`（`lib/index.js:176`）
- 答者缺失 / 抛错 → `unavailable`；返回词表外的值 → 归一为 `unavailable`（`lib/index.js:167-176`）
- `allowed-once` 是**唯一**授权形态，且只对本次请求的那个动作生效（`lib/index.js:26`）

→ **推论 B**：不确定性的**唯一合法退化方向是交回人类**（`next()` → 最终落到 `unavailable` → 沙箱保持拒绝）。插件里所有"失败路径"默认 `ask`、`failOpen: "ask"`、AI 异常交人类，不是保守偏好，而是这条公理的直接系。

### 1.3 接缝是排他的（契约）

`waterfall` 语义：第一个**不调 `next()`** 的监听者独占决策槽位，后续监听者收不到该请求。`{ prepend: true }` 注册者被 `unshift` 到头部。

→ **推论 C**：这不是"辅助插件"，是**接管插件**。同一个 profile 装第二个审批裁决插件，被旁路的一方**静默失效，不报错、不告警**（`docs/security.md:44-68`）。

### 1.4 审计归属在宿主（契约）

`approval/asked` + `approval/decided` 事件对由宿主在 `request()` 内写入，且必须在打开的 turn 内（`lib/index.js:130-145`）。

→ **推论 D**：插件**不需要也不应该**自建审批台账。它不实现"哪个请求被批准了"这个权威记录，只追加自己的**决策过程**日志（`index.js:1004` `makeRecorder`）。这是正确分工：权威状态在宿主，插件只提供可观测性。

## 2. 决策结构：为什么必然是一条有序链

把自动审批形式化为函数 `decide(r) → {allow, ask, deny}`。三种判定资源的性质完全不同：

| 资源 | 延迟 | 边际成本 | 错误形态 |
|---|---|---|---|
| 确定性规则匹配 | ~0 ms | 0 | 只有**匹配设计**错误，无真伪问题 |
| LLM 判定 | 秒级 | token | 概率性；输入可被影响 |
| 人类判定 | 人读得懂 | 注意力 | 接近 0 错误，但对"被打断"有成本 |

**（实测）** 中位延迟：规则命中 `1 ms`；AI 判定 `4632 ms`。

→ 任何理性系统必须**把确定性结论排在前面**：能零成本确定的结论，绝不该付模型调用；模型给不出结论时，才动用人这个最贵也最可靠的后备。"规则 → AI → 人类"不是产品口味，是单位成本下可靠性排序的结果。

同一条推论还给出另一个结论：**链上每一环的失败方向必须指向下一环，而不是指向"放行"**（推论 B）。插件里 `failOpen` 的默认值、`judgeWith` 的异常归一、候选链耗尽后的处置，全部服从这一条。

## 3. 规则层：确定性授权的合法性前提

### 3.1 全插件最核心的一步：字符串 → 执行效果不是单射

规则匹配的是**文本**。而 shell 文本到"实际执行什么"的映射是多对一的：

- `git status` 与 `git status; rm -rf /tmp/x` 共享前缀
- `cat x` 与 `cat /dev/null > x` 共享前缀
- `echo '$(rm -rf /)'`（单引号，不展开）与 `echo "$(rm -rf /)"`（双引号，展开）**文本几乎一样，语义相反**

`allow` 是三个动作里**唯一扩张权限**的动作。因此：

> **确定性授权的合法性前提，是输入的 argv 可被信任。**

→ 这就是形状闸门：bash/pwsh 的 `allow` 规则只在 `classifyCommand` 判定为 `simple`（单条纯命令）时才可能命中（`rules.js:128-131`；`shell-shape.js:54-58`）。复合、重定向、替换、变量、通配、控制流、赋值、换行一律 `opaque`；**ask/deny 不受闸门限制**，因为它们站在 fail-safe 一侧。

`2026-09-22` 审查项 1 复现的六条越权放行，全部是这一条缺失时的必然产物。

### 3.2 求值顺序由安全偏序决定

三个动作的安全偏序是 `allow ⊂ ask ⊂ deny`。求值必须**从最保守的一端开始**（`rules.js:158-177`：外层循环 `deny → ask → allow`）。

否则一条宽泛的 allow 会吞掉同一列表里更窄的 deny——"优先级"只在**已经匹配上**的规则之间成立，救不了被前缀包住的后半段命令。所以规则列表的书写顺序可以被忽略，但**动作的偏序不可协商**。

### 3.3 argv 前缀为什么强于 glob

结构化规则 `{tool, pattern: [git, status], action: allow}` 比较的是 **argv 数组**（`rules.js:133-148`），即"已被解释过的文本"；glob 比较的是原始字符串，即"看起来像"。

### 3.4 从"读"剪掉"写"的输入空间

- `forbidOptions: ["--output"]` —— `git diff --output=x` 把只读命令变成写文件
- `pathGuard: "workspace-relative"` —— `cat` 只在工作区内自动放行

两者都是同一操作：把"这条命令的语义漂移到写盘"的输入空间从授权域里剪出去。

### 3.5 判定的域必须是**解析后**的域

静态检查（无绝对路径、无 `~`、无 `..`、无盘符）能挡明显的逃逸，但挡不住 `ln -s /etc/ssh ./link`。因此 `pathGuard` 的最终判定是 `realpath` 复核：每个路径参数的**真实**实体必须落在工作区根内，任何解析失败都算拒绝（`index.js:725-745`）。

同一个道理在形状判定里再出现一次：判定必须在**原文**上做，脱敏必须在**之后**做。顺序颠倒会把一个不透明命令"洗"成可批准的命令（`index.js:820-826` 的注释把因果写得很清楚）。

### 3.6 deny 必须窄，因为 deny 剥夺的是人类

`deny` 的语义是"人类永远不会被问到"（`index.js:96-99`）。所以默认 deny 只覆盖后果不可逆的动作，且要用 `*` 前缀抓"藏在分隔符后面"的破坏命令（`*rm -rf /*`）；而发布、凭据、审批配置一律是 `ask` 而非 `deny`——它们需要人的判断，不需要机器的独断。

## 4. AI 层：不可信输入 × 不可信输出

judge 是一个 LLM，它拿到的是**模型自己生成的命令文本**——不可信输入；它输出的是**文本**——不可信输出。两条边界都要处理。

### 4.1 输入侧：三道隔离

1. **政策与证据分离**：固定政策写在提示词前段，请求体是 `{"toolName","command","reason"}` JSON（`judge.js:56-70`）。
2. **统一脱敏边界**：prompt、审计、拒绝反馈、provider 错误诊断**同一个** `redactSensitive`（`redact.js:25-36`）。要点是保留**形状**（标签、URL 参数名、路径）——judge 仍然需要认出"这条命令在处理凭据"。
3. **上下文只喂骨架**：`transcript: "short"` 下，成功 stdout **一律不喂模型**（原始工具输出是最容易打字的间接注入面），plugin 自身注入的消息也不回灌（`transcript.js:120`）——后者的理由见第 6 节。

### 4.2 输出侧：闭合枚举 + 唯一可解析

- 判定必须落在 `risk ∈ {low,medium,high}` × `authorization ∈ {allow,ask,deny}` 的闭集里（`judge.js:118-134`）
- **多裁决一律非法**：出现两个及以上"判决形状"的对象 → 该候选失败，而不是"取第一个"（`judge.js:150-164`）——否则"先 allow 再 deny"的输出会被解读成 allow

**必须诚实的一点**：枚举约束的是**输出格式**，不是**模型的判断**。它不能使 judge 免于提示注入。真正的硬边界永远在沙箱与宿主策略，`deny` 规则是加速拒绝，不是强制（`docs/security.md:38-42`）。这一条是审查打回的产物，README 里"因此不存在注入面"的旧表述已被删除。

### 4.3 `riskTolerance` 的真实语义：不是硬上限

```js
if (verdict.authorization === "allow" || verdict.authorization === "deny") return verdict.authorization;
return RISK_RANK[risk] <= RISK_RANK[tolerance] ? "allow" : "ask";   // judge.js:174-179
```

→ AI 的 `allow`/`deny` 是**直接采纳**的；容忍度**只在 AI 说 `ask`（"我不敢定"）时才参与**。

后果：`{risk: "high", authorization: "allow"}` 在 `tolerance: "low"` 时**会放行**；`{risk: "medium", authorization: "ask"}` 在默认 `medium` 下会被改判放行。这是**有意识的设计**（用户授权与风险是两个轴），但也是本插件最容易误读的一处：容忍度不是风险闸门，风险等级不是硬上限。

### 4.4 候选链的正确判据

一条候选只有**给出可解析判定**才算答对（`judge.js:660-674`）。

这里踩过一个真实坑：空回复曾被视为"成功尝试"，于是链在空字符串上终止，配置好的 fallback 一个没花（审计里表现为 `ai-error` + 空 `rawOutput`）。修复后"空回复"与"有文本但无判决"都归为候选失败并推进——`dff99e5`。

链不因"换个模型看法不同"而推进，也不重试同一候选：judge 位于审批关键路径，多一次调用就是用户多付的延迟。

## 5. 不确定性的分类学：两种"不知道"必须分开

| 形态 | 含义 | 处置 | 是否受 `mode3OnAsk` 影响 |
|---|---|---|---|
| `evidence-incomplete` | **没看到操作**（参数缺失 / JSON 不可解析 / shell 无 command / 超过 `maxJudgeCommandChars`） | 不问 AI；`ai` → 人类，`ai-auto` → **拒绝** | **否**（`index.js:928-931` 显式豁免） |
| `ai-error` | 看到了但**判不出**（超时 / 401 / 空回复 / 无判决） | 走 `failOpen`（默认交人类） | 是 |

程序必须自己拒绝"未审到的操作"，因为拿 `command: null` 去问模型，模型真的会答 `allowed-once`——`index.js:704-709` 的注释记录了这次实测。

**如果某个模式开关能把"没看到"变成"允许"，那这个开关本身就是绕过通道。** 所以 `evidence-incomplete` 在 `ai-auto` 下无条件拒绝，`mode3OnAsk: allow` 也管不到它。

## 6. 决策的语义后果：一次拒绝会污染后续推理

宿主把**所有**非授权结果硬编码成"用户拒绝"：

- `dsh-sandbox/lib/index.js:118` → `the user rejected escalating this ...`
- `dsh-tools/lib/index.js:3471` → `the user rejected tool "..."`

自动审批拒绝时，主 agent 读到的句子是错的——它会道歉、停下，或换个更隐蔽的路径重试。

第一性看：这是**观察者效应**。"谁做的这个决定"这条信息在返回语义里根本不存在（`OUTCOMES` 只有 4 态，没有来源），插件接管了决策槽位，却无法在该槽位里留下签名。

→ 只能事后修补：把插件自身产生的拒绝放入队列，在下一个 `agent/pre-step` 注入一条 `source.kind: "plugin"` 的更正消息（`index.js:1233-1257`）。

这个修补自己带来**二次风险**，且代码里已按风险处理：

1. 注入消息进入会话历史 → `transcript` 必须**排除 plugin 源**，否则拒绝理由会回流给 judge，形成自我强化（`transcript.js:120`）
2. 队列必须有上限（`denyFeedbackMax: 3`，丢最旧）
3. 源头文案改不了（`docs/security.md:34`）——这是下游修正的固有代价

另外：只有插件**自己**产生的拒绝才入队。人类在 GUI 里的拒绝走另一个答者、不经插件，绝不会被误标成"自动拒绝"。

## 7. 正交维度：模式

`dsh` 的沙箱模式回答"边界在哪"；`approval-mode` 回答"边界被触碰后谁来裁"。两者正交——这正是原生 dsh 缺失的那一档。

- `manual`：完全旁路（连审计都不写）→ **可退化为"未安装"**。这是可逆性的设计：任何时候都能安全退出。
- `ai`：规则 → AI → `ask` 交人类
- `ai-auto`：规则 → AI → `ask` 永不交人类

`ai-auto` 不是"更自动的 ai"，而是**方向翻转**：人类这个最可靠的后备从链上被移除，所以

- prompt 变体禁掉 `ask`，并把"不确定时倾向 ask"改写成"倾向 deny"（`judge.js:37-46`）
- `mode3OnAsk` 决定 `ask` 的去向，**默认 `deny`**（`modes.js:59-62`）

可靠性链上少一环，整条链的失败方向就必须整体转向保守。这不是同一个策略的两个参数。

## 8. 实测复核（本机 684 行审计日志）

| 维度 | 数值 |
|---|---|
| 决策总数 | 196（其余 488 行为 `plugin-loaded` 等事件记录） |
| 判定来源 | `rule` 23 / `ai` 68 / `ai-error` 105 |
| 中位延迟 | `rule` 1 ms / `ai` 4632 ms |
| 结果 | `allow` 54 / `ask` 123 / `deny` 19 |
| 放行来源 | `allow|ai` 47、`allow|rule` 7 |
| AI 判定的风险分布 | medium 46 / high 21 / low 1 |

三条值得记录的观察：

1. **"失败不放行"这条不变量在真实运行中成立**：105 条 `ai-error` 没有一条产出 `allowed-once`；102 条落到 `ask`（交人类），3 条 `deny` 来自早期的 `failOpen: deny` 配置。
2. **AI 层的实际可用性远低于其设计的优雅程度**：105 / 173 ≈ 61% 的判定尝试没有产出可解析判决，前半段日志里这个比例更高。
3. **（推断）失败高峰与配置相关**：`2026-09-29`(17) 与 `09-30`(16) 的 `unparseable` 高峰落在 `maxTokens=512` 时期；`09-30 18:52` 提到 2048、`19:13` 超时放到 60 s 之后，日志中不再出现 `ai-error`（末尾三条均为 `judgeAttempts=1` 的正常判定）。时间上共变、机制上吻合（推理型模型把预算烧在思考阶段、吐不出 `text-delta`），但**没有做受控实验**，只能作为排查方向。

结论：这个插件的确定性收益在规则层（23 次零延迟定论），概率性收益在 AI 层（47 次放行）。审计日志的真实价值是让"AI 层到底有没有在工作"变成可读的数字——上面第 2、3 条就是靠它发现的。

## 9. 结构性张力（按严重度，均为真实约束而非缺陷）

1. **优先级来自时序，不来自声明**。`ctx.on("approval/request", handler)`（`index.js:1406`）**没有** `{ prepend: true }`。它之所以排在人类弹窗之前，是因为浏览器侧的人类答者要等客户端连上来才注册（`dsh-client-ui-approval/lib/client.js:355` 的 remote 桥），插件注册更早。任何在插件之前注册的宿主答者都会抢答——这与"同一 profile 只装一个裁决插件"的要求是同一个根因。
2. **提示词走 `user` 角色**（`judge.js:66-69`），固定政策与不可信请求体在同一条 `user` 消息里。`0.2.0` 的 system 通道未被使用；这是已知的注入面收敛方向（审查建议项 5）。
3. **AI 的 `allow` 不受容忍度约束**（见 4.3）。这是设计，但需要在任何"把它当安全边界"的期待里明说。
4. **无拒绝熔断**：同一动作可以被反复尝试；审查建议增加连续拒绝熔断与限次人工覆盖。
5. **`deny` 的边界不是强制的**。规则里的 deny 是"加速拒绝"，绕开它的路径（换解释器、编码、写入脚本再执行）只能由 AI 层与沙箱兜。

## 10. 最小不变核

如果把可用性与体验全部剥离，安全性所依赖的只有五条：

1. **形状闸门**——`allow` 只对 argv 可信的单条命令生效
2. **动作偏序**——`deny > ask > allow`，与列表顺序无关
3. **证据门槛**——未审到的操作永不放行，且不受模式开关影响
4. **fail-closed 默认**——任何失败都向"交回人类"退化
5. **唯一裁决解析**——多裁决/空回复/非法枚举一律视为失败

其余部分（模型选择、fallback 链、transcript、UI 卡片、拒绝反馈文案、审计字段）都是可以整块替换的体验层：删掉它们，插件仍然安全，只是不好用。

反过来读：**这五条中任意一条被改坏，插件就从"自动化"退化成"绕过通道"**——`2026-09-22` 审查里被确认的六个问题，恰好逐条命中这五条。
